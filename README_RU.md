# FTTH/PON Planner Toolkit

Повторяемый конвейер проектирования сельских/пригородных сетей FTTH/PON по спутниковому изображению и GIS-данным.

## Зачем создан

Инструмент фиксирует выводы из проекта по нескольким населенным пунктам ВКО. Главная проблема ручного/генеративного подхода — можно получить визуально убедительную карту, которая не совпадает с количественной ведомостью. Поэтому здесь **источником истины является единая GIS-геометрия**, а карта, CSV и спецификация строятся из одних и тех же объектов.

Ключевой принцип: **сначала данные и жесткие ограничения, потом отрисовка**.

## Конвейер

1. Получение/подготовка исходного изображения.
2. Геопривязка: предпочтительно GeoTIFF; для JPG/PNG — известный bbox.
3. Идентификация зданий и классификация:
   - `private` — частный дом;
   - `mdu` — многоквартирный жилой дом;
   - `review` — объект, требующий проверки.
4. Идентификация дорог или загрузка готового дорожного GeoJSON.
5. Задание/выбор точки OLT.
6. Построение графа дорог и трассировка.
7. Проектирование PON:
   - каждый подтвержденный частный дом = 1 drop = 1 порт FAT;
   - FAT 1×8 или 1×16 по фактическому числу домов;
   - не более 32 частных домов на PON по умолчанию;
   - при двух FAT дерево строится через PLC 1×2;
   - МКД — отдельный ввод/PON без выдумывания квартирности;
   - FAT → муфта → OLT только по дорожному графу;
   - контроль оптического бюджета;
   - расчет емкости фидерного кабеля с запасом;
   - **емкость муфты по сваркам = числу волокон полностью свариваемого входящего кабеля**: одна сварка соединяет два волокна.
8. Детерминированное наложение сети на исходное изображение.
9. Формирование GIS и спецификаций.

## Почему итоговую инженерную карту нельзя рисовать генеративно

Генеративное изображение полезно как эскиз, но оно может добавить/удалить FAT, PON, дропы и подписи. Для рабочей карты этот toolkit использует `Pillow` и рисует **точно те же линии**, которые записаны в `network.geojson` и CSV.

## Входные режимы

### Здания

Рекомендуется `buildings.mode: geojson` — контуры/центроиды зданий из GIS, кадастра или специализированной модели сегментации.

`buildings.mode: auto` — консервативный классический CV-детектор кровель. Он нужен как стартовая точка и обязательно формирует класс `review`; не считать его кадастровым подтверждением.

Авторитетное число домохозяйств используется как QA-проверка. По умолчанию скрипт **не придумывает недостающие дома** ради совпадения с таблицей.

### Дороги

Рекомендуется `roads.mode: geojson`.

`roads.mode: auto` — резервный алгоритм по низкой насыщенности/яркости и скелетизации. На карьерах, полях, грунтовых площадках и тенях он требует проверки.

### OLT

Рекомендуется `olt.mode: fixed` с подтвержденными координатами существующего/планируемого объекта связи.

`olt.mode: auto` выбирает медианную точку дорожного графа по абонентам и маркирует результат как требующий полевой проверки. По спутниковому снимку нельзя надежно доказать назначение здания как объекта связи.

## Запуск

```bash
python ftth_pon_planner.py init project.yaml
# отредактировать project.yaml
python ftth_pon_planner.py run project.yaml
```

## Основные выходные файлы

- `network_map.png` — детерминированная итоговая карта;
- `network.geojson` — вся сеть;
- `buildings.geojson` — классифицированные здания;
- `roads.geojson` — дорожный слой;
- `drops.csv` — каждый объект и индивидуальная длина drop;
- `fats.csv` — FAT, емкость и загрузка;
- `muftas.csv` — муфты, входящий кабель и сварочная емкость;
- `pons.csv` — загрузка PON и контроль бюджета;
- `feeder_cable_by_capacity.csv` — физический фидер по емкости кабеля;
- `specification.csv` — агрегированная спецификация;
- `qa_report.json` — автоматические проверки.

## Обязательные проверки качества

Перед выпуском проекта проверьте:

- `all_private_have_one_drop = true`;
- число частных домов соответствует подтвержденному слою;
- `fat_over_capacity = 0`;
- `pon_over_32 = 0`;
- `pon_budget_review = 0` или все исключения разобраны;
- каждая муфта имеет правильный входящий кабель и достаточную сварочную емкость;
- каждый МКД учтен как отдельный ввод, но его квартиры не выдуманы;
- OLT подтвержден владельцем/оператором или полевым обследованием;
- дороги и разрывы дорожного графа визуально проверены;
- закупочная длина учитывает монтажный запас, но физическая длина трассы не смешана с суммой логических PON-путей.

## Практические нюансы, учтенные в коде

- Отдельно хранятся длина индивидуального дропа и длина общей физической кабельной инфраструктуры.
- Фидерный кабель считается по нагрузке PON-волокон на каждом дорожном сегменте, затем округляется до стандартной емкости.
- Сумма маршрутов PON не используется как физическая длина кабеля, если магистральные участки общие.
- Для FAT при 17–24 абонентах формируется группа 1×16 + 1×8; при 25–32 — две группы до 16.
- При двух FAT в дереве учитывается каскад `1×2 + 1×8/1×16`, что ограничивает итоговый split ratio 1:16 или 1:32.
- Оптический бюджет считается по худшему ODN внутри каждого PON.
- Для МКД внутренний коэффициент деления не назначается до получения квартирности.
- Муфта: 8F → 8 сварок, 12F → 12, 24F → 24, 48F → 48 при полной сварке входящего кабеля. Удвоение не выполняется.

## Что нужно заменить для промышленной эксплуатации

Автоматическое распознавание зданий и дорог в этом репозитории — универсальный baseline. Для массовой обработки лучше подключить обученные модели сегментации/детекции. Архитектура специально разделяет детекцию и проектирование: можно подать качественные `buildings.geojson` и `roads.geojson`, не меняя алгоритм PON.

## Сохранение результатов

Сам каталог проекта можно хранить в GitHub/корпоративном Git, на сетевом диске или в рабочем проектном хранилище. Для воспроизводимости сохраняйте вместе:

- исходное изображение или ссылку/идентификатор источника;
- YAML-конфиг;
- входные GeoJSON;
- `qa_report.json`;
- итоговые GIS/CSV/PNG.
